# 문제 해결 사례: 120화 원고를 검수 가능한 데이터로 바꾸기

## 한 줄 결과

35개 Markdown 문서에 혼재하던 120화의 초안·정본을 240개 안정 버전으로 분할하고, 실제 원문을 공개하지 않으면서 설정 근거·충돌 후보·사용자 판정을 연결했다.

## 역할과 범위

- 형태: 개인 포트폴리오 프로젝트
- 역할: 문제 정의, 데이터 모델, 가져오기 파이프라인, React UI, 연속성 엔진, 평가 설계, CI/배포
- 범위: 서버와 외부 AI API 없이 재현 가능한 로컬 우선 프로토타입

## 문제와 제약

원고는 35개 문서에 5~10개 회차씩 묶여 있었고, 초안·완성본·설정집·로드맵은 파일명으로만 구분됐다. 핵심 제약은 두 가지였다.

1. 회차가 수정되어도 근거와 판정을 다시 찾을 수 있어야 했다.
2. 실제 원고와 세부 설정은 공개 저장소와 데모에 들어가면 안 됐다.

## 핵심 의사결정

| 선택 | 고려한 대안 | 이유 |
|---|---|---|
| 안정 ID와 내용 해시 분리 | 파일명 또는 해시만 ID로 사용 | 수정 후에도 회차 정체성은 유지하고 내용 변경만 감지하기 위함 |
| 비공개 매니페스트 + 공개 합성 데이터 | 원고 일부 마스킹 | 문장 조각으로도 작품을 추정할 수 있어 원문을 전혀 공개하지 않음 |
| 로컬 규칙 기준선 우선 | 처음부터 LLM API 사용 | 비용·보안·재현성을 고정하고 실패 유형을 먼저 측정하기 위함 |
| IndexedDB 우선 + 버전 마이그레이션 | `localStorage` 단일 저장 | 240개 버전 이상을 다루고 스키마 변경에 대응하기 위함 |

## 구현과 실패

### 1. 원고 구조화

- 원본을 압축 백업하고 SHA-256으로 무결성을 기록했다.
- `## N화`, `# N화 초안` 머리말을 기준으로 회차를 분할했다.
- `작품-회차-상태`로 안정 ID를 만들고 중복·분할 실패를 자동 검사했다.
- 참고 문서의 제목을 로컬 설정 후보로 추출해 수작업의 출발점을 만들었다.

### 2. `rule-v1`의 실패

v1은 직접 등록된 충돌 표현은 10/10으로 찾았지만 간접 표현, 정상 변화, 회상·거짓말·불확실한 기억을 처리하지 못했다. 전체 결과는 14/70이었다. “검색 성공”과 “충돌 판정 성공”을 분리해 측정하지 않았다면 숨겨졌을 실패였다.

### 3. `rule-v2`의 개선

- 별칭을 정본 대상명으로 정규화한 뒤 검색했다.
- 설정별 직접 충돌 표현과 간접·의미 패턴을 분리했다.
- 시간축, 발화 유형, 기억 신뢰도를 판정 입력으로 올렸다.
- 단정할 수 없는 문장을 오류가 아닌 `문맥 필요`로 분류했다.

## 수치로 검증한 결과

| 항목 | 결과 |
|---|---:|
| 고유 회차 | 120 |
| 초안 / 정본 버전 | 120 / 120 |
| 중복 ID / 분할 경고 | 0 / 0 |
| 참고 문서 제목 기반 설정 후보 | 81 |
| 공개된 실제 원문 | 0 |
| v1 / v2 회귀 통과 | 14/70 / 70/70 |
| v1 / v2 문맥 식별 | 0/30 / 30/30 |
| 자동화 테스트 | 18개 |
| 외부 API 비용 | $0 |

## 아직 증명하지 못한 것

- 70/70은 알려진 실패 유형의 회귀 결과이며 새 작품에 대한 일반화 정확도가 아니다.
- 실제 작가의 검수 시간이 얼마나 줄었는지는 아직 측정하지 않았다.
- 시간적 효과를 주장하려면 수작업과 StoryOps로 같은 오류 20건을 찾는 블라인드 태스크가 필요하다.

이 한계를 숨기지 않는 이유는 포트폴리오의 핵심 성과가 “정확한 AI”가 아니라, **데이터 경계를 지키며 실패를 재현하고 개선을 비교할 수 있는 운영 구조**를 만든 것이기 때문이다.
